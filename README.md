# Crypto Oracle

Backend-система для прогнозирования движения цен криптовалют с бизнес-логикой управления заявками. Тестовое задание на позицию Full-stack разработчика.

**Стек:** FastAPI, SQLAlchemy, Pydantic, Streamlit, SQLite, Pandas.

---

## System Design

### Архитектура

Трёхслойная архитектура с разделением ответственности:

- **Frontend (Streamlit):** тонкий клиент, отображение данных, приём ввода.
- **Backend (FastAPI):** REST API, бизнес-логика прогнозирования, оркестрация.
- **Data (SQLite + SQLAlchemy):** справочники, заявки, сырые метрики, аудит-трейл.

### Ключевые решения

- **Детерминированность:** расчёт скоринга выполняется только по сохранённым в БД метрикам. Повторный запрос даёт идентичный результат.
- **Разделение данных:** `raw_data` хранит исходные метрики с источником; `predictions` — производные результаты. Это позволяет верифицировать расчёты и менять алгоритм без потери истории.
- **Жизненный цикл:** прогноз — бизнес-сущность со статусами `draft → collecting → active → fulfilled / expired / cancelled`. Каждое изменение фиксируется в `status_history`.
- **Изоляция зависимостей:** внешние API инкапсулированы в `data_collector`. Добавление нового источника не затрагивает бизнес-логику.

### Ограничения и точки роста

- SQLite заменяется на PostgreSQL изменением одной строки конфигурации.
- Синхронный сбор данных может быть вынесен в Celery/RQ для production.
- Rule-based скоринг заменяется на ML-модель без изменения API-контракта.
- Отсутствуют аутентификация и идемпотентность (добавляются при масштабировании).

## Соответствие критериям задания

| Критерий | Реализация |
|----------|------------|
| Область прогнозов | Криптовалюты (BTC, ETH, SOL), горизонт 24ч |
| 2 реальных источника | CoinGecko API + Alternative.me API |
| База данных | SQLite: 4 таблицы (справочник, заявки, метрики, история) |
| Список объектов | `GET /assets`, реестр прогнозов с фильтрацией |
| Карточка прогноза | Вердикт, уверенность, риск, аргументы, сырые данные |
| Алгоритм | Rule-based scoring с прозрачными весами |
| Сходимость цифр | Детерминированный пересчёт из сохранённых метрик |
| Уверенность | `min(\|score\| / 50, 1.0) × 100%` |
| Риск | Рассчитывается из волатильности и индекса F&G |
| Ошибки модели | Scheduler сверяет прогноз с фактом через 24ч |
| Без реальных денег | Только аналитика, без интеграции с биржами |

## Структура БД

| Таблица | Назначение | Ключевые поля |
|---------|------------|---------------|
| `assets` | Справочник активов | `symbol`, `external_id`, `quote_currency` |
| `predictions` | Заявка на прогноз | `asset_id`, `quote_currency`, `status`, `score` |
| `raw_data` | Сырые метрики | `prediction_id`, `source`, `metric`, `value` |
| `status_history` | Аудит-трейл | `from_status`, `to_status`, `reason` |

**Жизненный цикл:** `draft → collecting → active → fulfilled / expired / cancelled`

---

## Алгоритм скоринга

| Правило | Условие | Вес |
|---------|---------|-----|
| Импульс цены | изменение за 24ч > ±2% | ±20 |
| RSI(14) | >70 / <30 | −30 / +30 |
| Fear & Greed | <25 / >75 | +25 / −25 |
| Объём торгов | изменение за 24ч > ±20% | ±15 |

**Итог:** `score ∈ [−100, 100]` → вердикт (Strong Buy / Buy / Neutral / Sell / Strong Sell).

## API Endpoints

| Method | Endpoint | Назначение |
|--------|----------|------------|
| `GET` | `/assets` | Список активов |
| `POST` | `/predictions?asset_id=N` | Создать прогноз (полный цикл) |
| `GET` | `/predictions?status=X` | Реестр с фильтрацией |
| `GET` | `/predictions/{id}` | Карточка с сырыми данными |
| `PUT` | `/predictions/{id}/status` | Смена статуса |
| `GET` | `/predictions/{id}/raw_data` | Сырые метрики |
| `GET` | `/predictions/{id}/history` | Аудит-трейл |
| `GET` | `/health` | Health check |

Swagger UI: `http://localhost:8000/docs`

## Проверка сходимости

1. `POST /predictions?asset_id=1` — запомнить `score`.
2. `GET /predictions/1/raw_data` — извлечь метрики.
3. Пересчитать score вручную по таблице весов.
4. Результат совпадает с сохранённым значением.

Расчёт детерминирован: идентичные входные данные дают идентичный score.

## Определение ошибок модели

`scheduler/auto_collect.py` (запуск по cron / Task Scheduler):

1. Находит прогнозы со статусом `active` и истёкшим `expires_at`.
2. Запрашивает фактическую цену актива.
3. Сравнивает направление прогноза с фактическим изменением.
4. Меняет статус на `fulfilled` или `expired`.
5. Записывает фактическое изменение в `status_history`.

Метрики качества: Directional Accuracy, Confidence Calibration.
